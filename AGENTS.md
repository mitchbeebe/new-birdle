# Code style
- Use ruff for linting and formatting
- Use uv to manage dependencies
- Follow PEP 8 style guidelines

# Engineering Philosophy
- Think before coding: state assumptions, surface tradeoffs and ambiguous interpretations, push back if a simpler approach exists, and stop to ask when genuinely confused rather than guessing silently.
- Simplicity first: write the minimum code that solves the problem — no speculative features, abstractions, or configurability beyond what was asked. If a senior engineer would call it overcomplicated, simplify.
- Surgical changes: touch only what the task requires. Don't refactor or reformat adjacent code, match existing style, and only remove dead code your change orphaned — mention other dead code instead of deleting it. Every changed line should trace to the request.
- Goal-driven execution: turn imperative tasks into verifiable goals (e.g. "fix the bug" → "write a failing test, then make it pass") and state a brief plan with a verification step for each stage of multi-step work.

# Agent Workflow
The user plans milestones and issues in the "Birdle" Linear project (team key `MIT`). From there, a per-milestone planner carries each issue through planning, implementation, and review, using `herdr` to spawn and coordinate everything.

Branches are never created through `gh stack init`/`add` — that requires shared local tracking state, which doesn't survive across the sibling worktrees this workflow depends on. Instead each issue's branch is created directly as its own worktree (`--base` = the branch of whichever issue it's `blockedBy` in Linear, or `origin/main` if unblocked — not creation order), and PRs are opened manually with `gh pr create`. `gh stack link` — which needs no local tracking — runs once at the end to register the finished chain of PRs as one GitHub stack.

- Milestone workspace: one per milestone, no dedicated worktree or branch. The planner is read-only (it never commits), so it works directly in the primary `birdle` checkout — matching upstream Herdr's own guidance that read-only investigation belongs in the shared checkout, and only actual implementation work earns a dedicated worktree. Canonical: before creating one, run `herdr workspace list` and check for an existing workspace on this repo already labeled `<milestone-name>`; if one exists, `herdr workspace focus <its-workspace-id>` it rather than creating a duplicate. Only if none exists, create fresh: `herdr workspace create --cwd /Users/mitchbeebe/Desktop/mitchbeebe/birdle --label <milestone-name>`, then `herdr tab rename <tab-id> agents` on its default tab. Because the checkout is shared with whatever else is active in it (including this session's own edits), the planner must never trust the working tree blindly — `git fetch` first, read pinned state via `git show origin/main:<path>` where it matters, and at minimum check `git status` and flag if the tree is dirty before acting on anything read from it. This is the planner's own home base — it never holds implementation work.
- Starting a milestone: the user asks a Claude Code session to stand up the milestone workspace and its `agents` tab, then spawn `<milestone>-planner` into that tab via `herdr agent start ... --model sonnet --effort high` (see "Role identity" below). That bootstrap session's job ends there — the user drives the planner's pane directly from then on.
- Planner loop: for each unplanned issue, read it from Linear, write a concrete plan (files, functions, sequencing, verification), and attach it to the issue. If planning surfaces a real dependency on another issue's unmerged work, record it as a `blockedBy` relation via `save_issue` (not just prose in the plan) before creating the branch — that relation is what `--base` above keys off. The planner never writes code, and never uses the in-process Explore/Agent tool for its own research — that goes through herdr panes/agents too, same as everything else. Once a plan is ready: create the issue's branch and sibling worktree in one step (`herdr worktree create --workspace w1 --branch <linear-id> --base <prev-linear-id-or-origin/main>`, no `--path` override needed since each branch name is unique), symlink `.env` in (`ln -s /Users/mitchbeebe/Desktop/mitchbeebe/birdle/.env <worktree-path>/.env` — worktrees only check out tracked files, and `.env` is untracked), spawn `<linear-id>-implementer` there with the plan, and move on to the next issue without waiting.
- One worktree per issue, no exceptions: the implementer and its reviewer both work in that issue's worktree; nothing is ever edited in the milestone workspace's shared checkout, and worktrees are never nested inside each other.
- Implementer: implements the plan on the issue's branch (already created by the planner) and commits there.
- Independent review: once the implementer believes it's done, it splits a sibling pane in the same worktree and spawns `<linear-id>-reviewer` — a fresh agent with no implementation history — to review the diff against the plan and this file. The reviewer never writes code, only reports findings; loop reviewer → implementer until it has none.
- Verification gate before opening a PR: `uv run ruff check`, `uv run ruff format --check`, `uv run ty check`, and `python manage.py test` must all pass on the issue's branch.
- Opening the PR: push if needed (`git push -u origin <linear-id>`) then `gh pr create --draft --base <prev-linear-id-or-origin/main> --head <linear-id> --title '...' --body '...'`, linking the Linear issue (`[LINEAR-ID](url)`) in the body. Once every issue in the milestone has an open PR, the planner runs `gh stack link <pr-numbers-in-stack-order>` (from anywhere — it needs no local state) to register the chain as one GitHub stack. Before linking — and before any implementer rebases a branch — the planner verifies chain integrity: `git merge-base --is-ancestor <base> <branch>` for every adjacent pair, and that each `blockedBy` relation still matches the actual branch base. If an implementer needs to rebase a branch, the planner first tells it which upstack branches/issues depend on it, so the rebase is known to require cascading rather than assumed complete on its own.
- Human review: PRs are opened as drafts for the user — no agent merges a PR or marks a Linear issue Done.
- Linear status & labels: use the `Claude` label group (`Planning`, `Implementing`, `Reviewing`, `Blocked`) plus `Needs human review`, swapping the label as the active phase changes (including each reviewer → implementer loop). Status is `In Progress` through planning/implementing/reviewing, `Blocked` if an agent needs human input mid-phase, and `In Review` (label → `Needs human review`) once the draft PR is open.
- Coordination is push, never poll: every handoff (reviewer → implementer, implementer → planner, planner → user) is the sender proactively notifying the recipient — `herdr agent prompt <recipient> "..."` for an agent, `herdr notification show <title> --body "..."` for the user. Don't loop on `herdr agent get`/`agent read` to check if a child is done. Block only for a genuine synchronous single-purpose handoff (e.g. a reviewer waiting on one fix), using `--wait`/`--until`. The planner stays unblocked — notify and move to the next issue rather than waiting out any one implementer/reviewer loop.
- Close out: once an issue's PR is open, the implementer notifies the planner and leaves its worktree in place — no `herdr worktree remove`. The human may still want to poke at the code directly in it while reviewing the draft PR, so worktrees are never torn down as part of normal close-out; only the user removes one, once they're done with it. If a worktree does get removed (by the user) and needs revisiting, use `herdr worktree create` (not `open` — `open` fails once the directory's gone; `create` adopts the existing branch automatically). Once every issue has an open PR and `gh stack link` has registered the finished chain, the planner notifies the user (`herdr notification show`); the milestone workspace, `agents` tab, and all issue worktrees stay up after that — only the user closes or removes them (`herdr workspace close`, `herdr worktree remove`), since the planner would otherwise be tearing down panes the user is still using.
- Role identity per spawn: `herdr agent start <name> --kind claude` execs plain `claude` directly — there's no role profile to load, so the herdr agent name (`<milestone>-planner`, `<linear-id>-implementer`, `<linear-id>-reviewer`) and the initial prompt (pointing it at this file's workflow and its specific task) are what establish the role for the session. Model/effort are native args after `--`: planner = `--model sonnet --effort high`, implementer/reviewer = `--model sonnet --effort medium`.
