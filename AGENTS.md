# Code style
- Use ruff for linting and formatting
- Use uv to manage dependencies
- Follow PEP 8 style guidelines

# Engineering Philosophy
- Think before coding: state assumptions, surface tradeoffs and ambiguous interpretations, push back if a simpler approach exists, and stop to ask when genuinely confused rather than guessing silently.
- Simplicity first: write the minimum code that solves the problem — no speculative features, abstractions, or configurability beyond what was asked. If a senior engineer would call it overcomplicated, simplify.
- Surgical changes: touch only what the task requires. Don't refactor or reformat adjacent code, match existing style, and only remove dead code your change orphaned — mention other dead code instead of deleting it. Every changed line should trace to the request.
- Goal-driven execution: turn imperative tasks into verifiable goals (e.g. "fix the bug" → "write a failing test, then make it pass") and state a brief plan with a verification step for each stage of multi-step work.

# Agent Workflow
The user plans milestones and issues in the "Birdle" Linear project (team key `MIT`). From there, agents carry each issue through planning, implementation, and review.

- Orchestration: a managerial Claude Code session spawns one `<milestone>-planner` per milestone, using the `herdr` skill, into a dedicated `agents` tab in the milestone's Herdr workspace (create it once per milestone if it doesn't exist) — never split panes inside the orchestrator's own tab. The planner stays alive for the whole milestone: it plans each issue in turn and directly spawns that issue's implementer → reviewer → implementer chain, so multiple issues' worker/reviewer pairs can be running at once under a single planner. The orchestrator's job is to stand up the worktree/workspace, spawn the planner, and relay the planner's status back to the user — it does not spawn implementers or reviewers itself.
- Coordination is push, never poll: every handoff in this workflow (reviewer → implementer, implementer → planner, planner → orchestrator, orchestrator → user) is the sender proactively notifying the recipient — e.g. the sender running `herdr agent prompt <recipient> "..."` into the recipient's pane — the moment it has something to report. A parent must never sit in a loop calling `herdr agent get`/`agent read` on a child to check whether it's done; that burns tool calls and context on repeated no-op status checks. The one exception is a genuine synchronous, single-purpose handoff where the sender has nothing else to do until the reply lands (e.g. a reviewer waiting on one specific fix) — there, block with `herdr agent prompt ... --wait` or `herdr agent wait ... --until` instead of polling. The planner in particular must stay unblocked: it notifies and moves on to the next issue rather than waiting for any one implementer/reviewer loop to finish.
- Linear status & labels: keep the issue's Linear status and label current as work moves through phases, using the `Claude` label group (`Planning`, `Implementing`, `Reviewing`, `Blocked`) plus the standalone `Needs human review` label. When an agent begins working a phase, set status to `In Progress` and label to the matching `Claude` label (`Planning` for the planner, `Implementing` for the implementer, `Reviewing` for the reviewer) — swap the label each time the active phase changes, including on every reviewer → implementer loop iteration. If an agent gets stuck and needs human input mid-phase, swap the label to `Blocked` (status stays `In Progress`) and swap back to the resumed phase's label once input arrives. Once the implementer opens the draft PR, set status to `In Review` and swap the label to `Needs human review`, replacing whatever `Claude` label was set — responsibility has passed to the user at that point.
- Worktree per milestone: create one git worktree per milestone, branched from a fresh `origin/main`, and name the worktree directory (and its Herdr workspace) for the milestone. All of that milestone's issue branches stack inside this worktree; there's no separate "milestone" git branch — the stack is rooted directly at `origin/main`. Place the worktree at `/Users/mitchbeebe/Desktop/mitchbeebe/<milestone-slug>` (sibling to `birdle`) via an explicit `--path` — do not rely on Herdr's configured `directory` default (`~/.herdr/worktrees/<repo>/<branch-slug>`), since every milestone worktree shares the branch name `main` and would collide there. Create it with `herdr worktree create --workspace w1 --path /Users/mitchbeebe/Desktop/mitchbeebe/<milestone-slug> --branch main --base origin/main --label <milestone-name>` (or `herdr worktree open --workspace w1 --path <milestone-dir>` if the directory already exists as a git worktree) — not a manual `git worktree add` plus a bare `herdr workspace create`. `w1` is the parent `birdle` Herdr workspace; passing `--workspace <parent-workspace-id>` is what nests the new workspace under it in the Herdr sidebar instead of creating a disconnected top-level space.
- Stacked branches per issue: inside the milestone worktree, use the `gh-stack` skill (`gh stack init` for the first issue, `gh stack add` for each one after) to stack one branch per issue on top of the previous one. Name each branch the lowercase kebab-case Linear issue ID (e.g. `mit-142`) — never a paraphrased title. The branch's PR carries the same name.
- One physical checkout per issue, always: the milestone worktree's own directory is a coordination anchor (where the planner runs `gh stack init`/`gh stack add` to create each branch) — it is never where an implementer edits files or runs git commands, even when only one implementer is active. As soon as an issue's branch exists, the planner gives it its own **sibling** Herdr worktree — `herdr worktree create --workspace <milestone-workspace-id> --branch <linear-id> --base <prev-branch-or-origin/main>` with no `--path` override, letting it land at Herdr's default `~/.herdr/worktrees/<repo>/<linear-id>` (safe here, unlike the milestone worktree itself, because each issue branch name is already unique — no collision to override for) — and points that issue's implementer at it. Never nest a worktree inside another worktree's directory: git worktrees share the same `.git` object database, so nesting confuses `.git` resolution and breaks tools (including `gh-stack`, see below) that walk up the directory tree looking for a repo root. This isolation is non-negotiable even for a single implementer, because `gh stack add` for the *next* issue branches from the current `HEAD` of the shared checkout — if any implementer has uncommitted changes sitting in that shared directory when the next `gh stack add` runs, those changes silently ride along onto the new branch and contaminate it. A separate worktree per issue makes that impossible: each implementer's edits live only in its own directory, so a branch can only pick up commits that were actually committed to it. The reviewer for an issue runs in that same worktree (read-only), not a separate checkout. Once an issue's PR is open and its tab closes, remove its worktree (`herdr worktree remove --workspace <that-issue's-workspace-id>`). A worktree is a fresh checkout of tracked files only — `.env` is untracked and won't be there, which breaks `python manage.py test` (and anything else needing local settings/secrets) until it is, and this is true of *every* worktree including the milestone-level one, not just per-issue ones. Immediately after creating each worktree, symlink (not copy) `.env` into it from the original `birdle` checkout — the actual source of truth for this file — e.g. `ln -s /Users/mitchbeebe/Desktop/mitchbeebe/birdle/.env <new-worktree-path>/.env`, before pointing the implementer at it. A symlink keeps one source of truth instead of copies that can silently drift.
- Planner: the milestone's `<milestone>-planner` picks up the next unplanned issue, reads it from Linear, produces a concrete implementation plan (files, functions, sequencing, verification steps), and attaches/updates it on the Linear issue. The planner never writes code. It also never uses the in-process Explore/Agent tool for its own research (codebase investigation, reading files across the repo, etc.) — everything, including its own investigation work, goes through herdr (sibling panes it opens or agents it starts via `herdr agent start`), consistent with the rest of this workflow running through herdr rather than in-process subagents. Once an issue's plan is ready, the planner creates the branch (`gh stack add <linear-id>` in the milestone worktree's own directory), immediately gives it its own sibling Herdr worktree with `.env` symlinked in (see above), spawns that issue's `<linear-id>-implementer` as that worktree's root pane, and hands it the plan — then moves on to plan the next issue rather than waiting for the implementer/reviewer loop to finish. Because issue branches stack on each other, the planner must have fully completed its own `gh stack add` (branch created, no leftover uncommitted state in the milestone worktree's own directory) for the prior issue before running it for the next one, even if that prior issue hasn't finished implementation or review yet.
- Implementer: spawned by the milestone planner into its issue's own sibling worktree, with the approved plan for its issue; implements directly on the issue's already-created branch (never runs `gh stack add` itself — that only happens once, from the planner, in the milestone worktree's own directory) and commits its work there.
- Independent review: when the implementer believes the change is done, it splits a sibling pane in its issue's worktree and spawns `<linear-id>-reviewer` there as a fresh agent with no implementation history, to review the diff against the plan and this file. The reviewer never writes code — it reports findings back to the implementer, who resolves them. Loop reviewer → implementer until the reviewer has no further findings.
- Verification gate before opening a PR: `uv run ruff check`, `uv run ruff format --check`, `uv run ty check`, and `python manage.py test` must all pass on the issue's branch.
- Opening the PR: once verification passes and the reviewer has signed off, try `gh stack submit --auto` first to push the branch and open its draft PR (base is the previous branch in the stack, or `origin/main` for the first issue in the milestone). The PR description links the Linear issue (`[LINEAR-ID](url)`). `gh stack`'s local tracking state lives in each worktree's own private git dir and is not visible from a sibling worktree, so `gh stack submit` reliably fails there with no local stack found. Don't try to fix or copy that tracking state over — fall back directly to a manual PR instead: push if needed (`git push -u origin <linear-id>`, often already done since the branch was pushed during creation) then `gh pr create --draft --base <previous-branch-in-the-stack-or-origin/main-if-first> --head <linear-id> --title '...' --body '...'` (linking the Linear issue in the body same as always). Double-check the intended base against the actual stack order (e.g. `git merge-base --is-ancestor <candidate-base> <linear-id>`) before creating it — don't assume adjacency from memory alone. Once *every* issue in the milestone has an open PR, the planner runs `gh stack link <pr-numbers-in-stack-order>` from the milestone worktree's own directory (which holds the authoritative local tracking) to register the whole chain as one GitHub stack — `link` works purely off existing branches/PRs and doesn't depend on any single worktree's local state, so it correctly stitches together PRs opened from different sibling worktrees.
- Human review: PRs are opened as drafts for the user to review — no agent merges a PR or marks a Linear issue Done. That stays an explicit user action.
- Close out the team: once an issue's PR is open, the implementer notifies the milestone planner and removes its issue's sibling worktree (`herdr worktree remove`, taking the `<linear-id>-implementer` and `<linear-id>-reviewer` panes with it). Don't leave finished roles or worktrees running. The `<milestone>-planner` and its `agents` tab stay up until every issue in the milestone has an open PR, at which point it notifies the orchestrator and the orchestrator closes it.
- Role identity per spawn: `herdr agent start` execs the `claude` CLI directly rather than using the in-process `Agent`/`Task` tool, so a spawned session has no built-in notion that it's supposed to act as "the implementer" or "the reviewer" — the herdr agent name (e.g. `mit-64-implementer`) is just a display label, not something the session itself sees. The `claude` CLI's own `--agent <name>` flag closes this gap: it loads the full profile from `~/.claude/agents/<name>.md` (persona/system-prompt body, tool restrictions, and model/effort from its frontmatter) for the whole session, not just the in-process tool — confirmed by testing it directly (tool list and status-bar model/effort matched the profile's frontmatter exactly). Every `herdr agent start ... --kind claude` call for a role in this workflow must therefore pass `--agent <role>` as a native arg after `--`, matching `.claude/agents/planner.md`, `implementer.md`, and `reviewer.md`: planner = `--agent planner --model sonnet --effort high`, implementer = `--agent implementer --model sonnet --effort medium`, reviewer = `--agent reviewer --model sonnet --effort medium` (the explicit `--model`/`--effort` are redundant with what `--agent` already loads from frontmatter, but kept for clarity and as a safety net against frontmatter drift).
